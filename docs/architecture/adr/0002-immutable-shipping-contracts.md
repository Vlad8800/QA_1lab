# ADR-0002 — Зберегти незмінні контракти розрахунку доставки

## Number and status

Номер: **0002**. Дата рішення про збереження контракту: **15.11.2026**. Статус: **Accepted — навчальний baseline**. Відповідальний: maintainer `Vlad8800`. Supersedes: немає. Superseded by: немає.

## Context

Історія ЛР7 містить `3aa6677` (FAIL: перезапис `final_cost`) та `2fb24e2` (PASS: frozen Value Objects), обидва від 31.10.2026. Поточний метод приймає `ShippingOrderSpec`, повертає `ShippingRateResult`; HTTP-адаптер і тести вже працюють із таким контрактом.

Цей ADR не видається за документ, створений 31.10. Він **сьогодні** фіксує рішення зберегти наявний контракт для подальшого супроводу та пояснює його обмеження. Числа Чепіна зі старої вручну розміченої матриці не є самостійним доказом правильності архітектури; рішення оцінюється за ясністю контракту й тестованою незмінністю.

## Alternatives

| Альтернатива | Переваги | Недоліки |
|---|---|---|
| П’ять primitive arguments і mutable dict result | Мінімальна кількість типів, проста сумісність | Легко переплутати аргументи чи перезаписати фінальний результат |
| Mutable dataclass | Іменовані поля, компактний об’єкт | Дозволяє випадкову зміну полів після створення |
| Frozen dataclass для входу й результату | Явні груповані контракти, `FrozenInstanceError` при звичайній зміні поля | Додаткові типи, зміна викликачів, незмінність не охоплює весь application state |
| Використовувати Pydantic request model усередині бізнес-логіки | Повторне використання валідації transport DTO | Зв’язує доменний контракт із HTTP-моделлю; політика незмінності потребує окремого налаштування |

## Decision

Зберегти `@dataclass(frozen=True)` для `ShippingOrderSpec` і `ShippingRateResult`. Перетворювати HTTP `OrderRequest` на специфікацію на межі API. Нормалізацію country/tier і перевірку ваги тримати в специфікації, а формулу — в її чистому методі `calculate_cost`.

Інтеграційний оркестратор `calculate_shipping_cost` залишає виклик tariff provider через Retry/Backoff/Fallback; його не називати чистою функцією. Збережені `get`, `__getitem__`, `to_dict` у result забезпечують сумісність наявних викликачів. Новий mutable фінансовий «проміжний стан» не вводиться без окремого обґрунтування.

## Consequences

Позитивні: іменована специфікація замість довгого набору параметрів; явно відділений вихід; звичайна спроба `spec.weight=...` або `result.final_cost=...` завершується `FrozenInstanceError`, що перевіряє наявний тест. Формула може перевірятися окремо від HTTP.

Компроміси: frozen не робить незмінним repository чи logging; зміна конструктора потребує оновлення API-адаптера, demos і тестів; вхідні та вихідні DTO не зберігаються у БД. Поточна арифметика використовує float і не стає бухгалтерським decimal-розрахунком лише завдяки frozen. Retry/fallback не створює Circuit Breaker, транзакцій чи гарантії зовнішнього SLA.

Критерій перегляду: зміна домену тарифів, вимог до грошової точності чи публічного контракту. Новий підхід описати новим номером ADR; цей запис за потреби отримує `Superseded by ADR-XXXX`, а первинні контекст/альтернативи/рішення зберігаються.
